# 운영 시스템 지식베이스 생성을 위한 입력·조사 기준 템플릿

이 문서는 코드를 읽어 일관된 업무 명세와 지식베이스를 만들기 위해 채워야 할 정보를 정리한다. Understand Anything의 범위 수집·작업 배정·근거·결과 규격·검사 방식을 참고하되, JSP·JavaScript·iframe·XML 설정을 통한 서비스 연결을 조사 중심으로 삼는다.

**현재 단계는 작성 기준 설계다. 아래 규칙이나 관계 형식이 분석 프로그램과 뷰어에 이미 구현된 것은 아니다.** `[작성]`은 실제 시스템 정보를 입력할 자리다. 모르는 부분은 `미확인`으로 남기며, 예시 식별자·규칙을 실제 사실로 사용하지 않는다.

## 1. 먼저 채울 최소 입력

전체 시스템을 한 번에 설명할 필요는 없다. 우선 아래 정보를 채우고 대표 기능 하나를 추적해 반복되는 연결 규칙을 확인한다.

| 입력 | 작성할 내용 |
|---|---|
| 분석 대상 | `[작성: 저장소·소스 루트, 시스템명, 조사할 기능 범위]` |
| 화면 진입점 | `[작성: 대표 JSP와 실제 화면명·식별자]` |
| 대응 JavaScript | `[작성: 해당 JSP의 인라인 script 또는 대응 JS 파일]` |
| 공통 화면 환경 | `[작성: 최상위 iframe 구성과 include.js 위치]` |
| 서버 호출 예시 | `[작성: 실제 호출 함수, 요청 식별자, 요청값을 만드는 코드 위치]` |
| 서비스 연결 설정 | `[작성: 해당 요청과 연결되는 XML 및 설정을 해석하는 코드 위치]` |
| 조사 결과 위치 | `[작성: 해당 프로젝트의 docs/codebase/ 등]` |

경로가 불명확한 부분은 검색으로 조사할 수 있다. 서비스 연결 규칙을 아직 모른다는 이유로 연결을 추측하지 않는다. 운영 비밀값이나 실제 고객 데이터를 입력하지 않는다.

## 2. 분석 범위와 기준

| 항목 | 입력 |
|---|---|
| 목적 | `[작성: 업무 명세, 장애 영향 확인, 유지보수 인수인계 등]` |
| 원본 루트·별칭 | `[작성: 화면/서버/배치/공통 라이브러리 등의 실제 루트와 별칭]` |
| 포함 범위 | `[작성: 기능·모듈·디렉터리·설정·SQL·기존 업무 문서]` |
| 제외 범위와 이유 | `[작성: 생성물, 바이너리, 캐시, 비밀값 등]` |
| 조사 기준 | `[작성: Git 커밋 또는 소스 스냅샷 식별자, 확인 날짜]` |
| 작업 트리 변경 | `[작성: 전체 dirty 여부와 조사 파일의 변경 여부]` |
| 환경 차이 | `[작성: 개발/운영별 XML, profile, 배포 설정 차이 또는 미확인]` |
| 쓰기 허용 범위 | `[작성: 지식 문서·관계 데이터 출력 위치]` |
| 조사 제한 | `[작성: 원본은 읽기 전용, 실행·DB·외부 접속 허용 여부]` |

XML·JSP·공통 script·SQL은 중요한 연결 근거일 수 있으므로 확장자나 디렉터리 이름만으로 제외하지 않는다. 외부 라이브러리는 관련 선언·소스를 제공받았을 때 필요한 범위만 조사한다. 자료가 없으면 경계를 기록한다.

Git이 없으면 파일 hash와 스냅샷 식별자를 기록하고 비교 한계를 남긴다. 같은 커밋이라고 작업 트리가 동일하다고 가정하지 않는다.

## 3. 시스템 연결 규칙 입력

여기가 이 시스템에 맞는 분석을 만드는 핵심이다. 규칙마다 **실제 예시 → 연결을 해석하는 근거 → 적용 범위 → 예외**를 기록한다. 파일명이나 문자열 일치만 발견했으면 후보 관계로 남긴다.

| 연결 | 채울 질문과 근거 |
|---|---|
| 화면 진입 → JSP | 화면명은 어디에 등록되는가? 메뉴·URL·설정 중 무엇이 JSP를 선택하는가? 실제 정의와 참조 위치는? |
| JSP → 대응 JS | 1:1 대응은 이름 규칙인가, script 선언인가, 별도 설정인가? 인라인 script와 외부 JS가 함께 있는가? |
| 상위 화면 → iframe | 프레임 구성·이름·주소는 어디에 정의되는가? 페이지 이동 시 실행 환경이 어떻게 바뀌는가? |
| include.js → 공통 JS | 로딩 목록과 순서는 어디에 있는가? 조건부 로딩·중복·교체가 있는가? |
| 화면 JS → 공통 함수 | 현재 프레임, parent, top 중 어느 컨텍스트에서 함수를 찾는가? 실제 접근식·정의는? |
| 이벤트 → 서버 요청 | 이벤트 등록 위치, 호출 함수, 화면명·자원명, 전달값 조립 규칙은? |
| 요청 → XML 정의 | 어떤 필드가 서비스 선택에 쓰이는가? namespace·접두사·환경별 차이는? 이를 해석하는 코드는? |
| XML → bean·서비스·처리 코드 | 실제 태그·속성, 참조 방식, 클래스·메서드 선택, 순서·조건은? |
| XML → 다른 XML | include·import·상속·별칭·덮어쓰기 규칙이 있는가? 실제 로딩 순서는? |
| 처리 코드 → 데이터 | DAO·mapper·SQL·프로시저·파일·외부 연동을 무엇으로 선택하는가? |
| 서버 응답 → 화면 | 응답 필드·데이터셋, 콜백, 오류 처리, 화면 반영 규칙은? |

### 연결 규칙 기록 양식

```text
규칙 ID: [작성]
설명: [작성]
적용 범위·환경: [작성]
출발점: [실제 상대 경로 + 식별자]
출발점에서 사용하는 연결 키: [실제 값 또는 값 조립 방식]
해석 근거: [설정/해석 코드의 상대 경로 + 식별자]
도착점: [확인된 상대 경로 + 식별자 / 미확인]
선택 조건·로딩 순서·우선순위: [작성 / 미확인]
예외·중복 키·동적 값: [작성 / 미확인]
확실성·조사 상태: [작성]
```

사용자가 설명한 시스템 특징은 조사 단서로 기록한다. 실제 코드와 설정에서 확인한 범위만 `코드 확인`으로 표시한다. Glue의 서비스 실행 방식이나 XML 의미를 일반적인 Spring 관례로 대신 채우지 않는다.

## 4. 조사 목록과 기능별 작업 배정

파일 목록은 전체 범위 관리용이다. 의미 조사 작업은 화면·기능의 처리 경로로 묶는다. import 관계는 보조 근거로 사용한다.

| 조사 대상 | 존재·구조 확인 | 의미 조사 상태 | 관련 기능 | 제외·미확인 이유 |
|---|---|---|---|---|
| `[상대 경로·식별자]` | `[확인/추출 제한/읽기 실패]` | `[미조사/부분 조사/확인됨/재확인 필요]` | `[기능 ID]` | `[작성]` |

파일 노드 생성, parser 성공, 원본 읽기, 업무 의미 확인은 각각 구분한다. 파일을 한 번 읽었다는 이유로 그 파일의 모든 기능을 확인했다고 표시하지 않는다.

각 조사 작업에는 다음을 고정해 전달한다.

- 대상 기능 ID, 조사 목적과 시작점.
- 관련 JSP·JS·XML·서버 코드·데이터 접근 파일 목록.
- 확인된 연결 규칙과 아직 해결되지 않은 연결 후보.
- 공통 script·서비스 등 다른 기능에서 재사용하는 근거.
- 이번에 확인할 질문과 완료 기준, 결과 저장 위치.

작업 순서는 **화면 진입 → 로딩 환경 → 이벤트 → 요청 구성 → XML 선택 → 서버 처리 → 데이터 변경 → 응답·화면 반영**을 기본으로 삼는다. 기능 특성에 따라 경로를 조정하고, 배치·이벤트 등 화면이 없는 기능은 해당 진입점부터 시작한다.

## 5. 기능별 업무 명세 양식

모든 기능이 같은 질문에 답하도록 한다. 해당하지 않는 항목은 이유와 함께 `해당 없음`, 자료가 없는 항목은 `미확인`으로 기록한다.

```markdown
# [기능명]

## 조사 기준
- 기능 ID·범위:
- 원본 별칭·커밋/스냅샷·확인 날짜:
- 조사 관련 변경 파일:
- 상태·확인한 범위·실행하지 않은 검증:

## 업무 목적과 용어
- 기능의 목적·사용자·관련 업무 개념:
- 문서에 명시된 의도와 코드상 동작의 차이:

## 시작 조건과 입력
- 진입 화면·이벤트·다른 기능의 호출:
- 권한·선행 상태·입력값·기본값·검증:

## 처리 흐름
| 단계 ID | 조건·동작 | 읽기·쓰기·부수 효과 | 다음 단계 | 원본 근거 |
|---|---|---|---|---|

## 업무 규칙과 분기
- 조건별 결과·예외·중복 요청·재시도:
- 규칙별 확실성·조사 상태·근거:

## 데이터와 상태 변화
- 핵심 데이터·키·관계:
- 변경 전 상태 → 조건 → 변경 후 상태:
- 트랜잭션 범위·실패 시 반영/복구 범위 또는 미확인:

## 결과와 오류
- 반환값·콜백·화면 반영:
- 실패 조건·오류 응답·로그·복구:

## 다른 기능과의 관계
- 선행/후속 기능·공유 데이터·이벤트·공통 처리:
- 관계 성립 조건과 원본 근거:

## 남은 질문과 한계
- 끊긴 처리 경로·누락 자료·업무 의도 질문:
- 정적 확인만으로 확정할 수 없는 동작:
```

## 6. 근거·확실성·조사 상태

주요 주장과 관계마다 아래 정보를 붙인다. 생성된 지식 문서를 그 설명 자체의 사실 근거로 순환 인용하지 않는다.

| 필드 | 기록 기준 |
|---|---|
| 주장 ID·설명 | 유지 가능한 ID와 조건을 포함한 구체적인 문장 |
| 근거 | 원본 별칭, 상대 경로, 함수·설정 키·XML ID·SQL 객체 등 식별자 |
| 원본 기준 | 내용 hash, 커밋/스냅샷, 실제 확인 날짜; 줄 번호는 보조 정보 |
| 확실성 | `코드 확인` / `문서 명시` / `추정` / `미확인` |
| 조사 상태 | `확인됨` / `부분 조사` / `재확인 필요` |
| 남은 질문 | 불명확한 조건·의도, 필요한 자료와 확인 위치 |

코드에 확인된 규칙도 연결된 처리의 일부가 미조사라면 그 범위를 구분한다. 정적 코드 확인을 실행 성공·운영 동작 검증으로 표현하지 않는다. 미확인 주장에는 근거를 만들어 붙이지 말고 부족한 자료를 적는다.

## 7. 관계 데이터 작성 기준

Markdown 명세를 먼저 읽기 좋게 작성하고, 같은 명세에서 탐색에 필요한 관계를 연결한다. 아래는 설계용 표현이며 현재 프로그램의 enum이나 JSON 규격을 확정한 목록이 아니다.

| 관계 분류 | 예시 의미 | 반드시 확인할 내용 |
|---|---|---|
| 기술 실행 | 로딩, 이벤트 처리, 요청 전송, XML 해석, 서비스 실행 | 선택 키, 컨텍스트, 조건·순서 |
| 데이터 | 읽기, 쓰기, 참조, 상태 변경 | 데이터 대상, 키·조건, 처리 주체 |
| 기능 의존 | 선행 조건, 후속 처리, 이벤트 전달 | 실제 조건·호출·사용 경로 |
| 공통 사용 | 공통 함수·서비스·데이터 사용 | 각 기능의 사용 위치와 역할 |
| 업무 의미 | 기능이 업무 규칙을 구현함 | 규칙 설명과 실제 구현 근거 |

관계에는 출발 ID, 도착 ID, 관계 의미, 조건, 근거와 조사 상태를 기록한다. 같은 공통 JS를 쓴다는 이유만으로 두 기능을 업무상 선행·후속 관계로 연결하지 않는다. 같은 테이블을 사용해도 영향이 생기는 키·조건이 다를 수 있다.

요청명이 동적으로 만들어지거나 XML 정의가 중복되는 경우 가능한 후보와 적용 범위를 남긴다. 해결되지 않은 대상을 확정 노드에 강제로 연결하지 않는다. ID는 파일명·표시명과 구분해 rename 후에도 의미가 같은 항목을 유지할 수 있도록 설계한다.

## 8. 일관성 검사와 완료 기준

| 검사 | 통과 기준 |
|---|---|
| 범위 누락 | 배정된 파일·기능마다 조사 결과 또는 제외·미조사 이유가 있음 |
| 연결 근거 | JSP·JS·XML·서비스 연결의 키·조건·해석 근거가 있음 |
| 참조 유효성 | 기록한 경로·식별자·관계 대상·문서 링크가 실제 존재함 |
| 기능 흐름 | 시작점에서 결과까지 추적했거나 끊긴 지점과 필요한 자료를 명시함 |
| 업무 규칙 | 중요 분기·권한·상태 변경·오류 처리에 근거 또는 미확인 이유가 있음 |
| 결과 형식 | 필수 항목·고유 ID·상태 표현이 일관되고 참조가 어긋나지 않음 |
| 조사 기준 | 이번에 확인한 주장만 현재 기준으로 표시함 |
| 사실 구분 | 추정·문서 의도·코드 사실·실행 미확인이 구분됨 |

형식 검사와 조사 체크리스트 완료는 업무 지식의 정확성 보장과 다르다. 업무 의도는 담당자의 확인이 필요할 수 있으며, 운영 환경이나 실행 결과가 필요한 항목은 정적 조사의 한계로 남긴다.

결과 보고에는 기능별 완료·부분 완료·미조사, 생성·갱신 문서, 주요 발견과 다음 확인 항목을 적는다. 막힌 기능 때문에 독립적으로 조사할 수 있는 다른 범위까지 중단할 필요는 없다.

## 9. 부분 갱신과 변경 영향

변경 파일뿐 아니라 위에서 확인한 연결 관계를 따라 갱신 후보를 선정한다. 관계를 사용했다는 사실과 실제 영향이 확인됐다는 사실은 구분한다.

| 변경 지점 | 재확인 후보 |
|---|---|
| 최상위 iframe·include.js | 로딩 환경·순서가 바뀌는 화면과 공통 함수 사용 기능 |
| JSP·대응 JS | 이벤트, 전달값, 요청 식별자, 콜백과 해당 기능 명세 |
| XML 정의·로딩 순서 | 해당 서비스를 선택하는 요청과 공유 bean·처리 흐름 |
| 공통 처리 코드 | 확인된 호출 기능과 입력·출력·오류·권한 규칙 |
| SQL·스키마·프로시저 | 읽기·쓰기 기능, 데이터·상태 명세와 실제 조건 |

근거가 바뀐 주장은 `재확인 필요`로 표시하고 이전 조사 기준을 보존한다. 영향을 조사한 부분만 새 기준으로 갱신한다. 의미 없는 변경이면 불필요한 문서 재작성을 피한다.

삭제·이름 변경은 대체 경로와 기존 문서 연결을 확인하고, 이력과 사용자 메모를 보존한다. parser 실패나 자료 누락을 실제 기능 삭제로 판단하지 않는다.

## 10. 역할과 산출물

| 담당 | 책임 |
|---|---|
| 사용자·시스템 담당자 | 대표 경로, 연결 관례, 업무 용어·의도, 운영 환경 차이를 제공·확인 |
| 기존 지식베이스 agent | 실제 코드·설정을 추적하고 업무 명세·근거·미확인 사항 작성 |
| 전용 skill | 조사 순서, 질문, 완료 기준, 출력 양식과 부분 갱신 원칙 고정 |
| 분석·검사 프로그램 | 파일 목록·hash·추출 결과·변경 후보·참조 검사·저장 관리 |
| 후속 변환 프로그램·뷰어 | 정해진 명세와 관계를 검사·변환하고 탐색 화면 제공 |

권장 산출물은 `README.md` 색인, 기능별 명세, 공통 처리·데이터·상태 문서, 조사 목록, 미확인 질문, 근거·관계 데이터다. 작은 범위는 문서를 합쳐도 된다. 빈 문서를 만들기 위해 범위를 늘리지 않는다.

먼저 기존 agent·skill을 이 기준에 맞춰 보강하는 방향을 검토한다. 대표 기능 하나로 작성 품질을 확인한 뒤 반복 가능한 규칙을 프로그램으로 옮긴다. 뷰어 형식에 맞추기 위해 업무 설명을 생략하거나 사실을 만들어서는 안 된다.

## 11. 채운 뒤 사용할 작업 요청 예시

아래는 조사 요청 양식이며 자동 agent 등록·실행을 설정하는 파일은 아니다.

```text
분석 대상 루트·별칭: [작성]
대상 기능과 시작점: [작성]
입력 자료: [실제 JSP·JS·XML·서버·데이터 파일과 연결 규칙]
조사 기준: [커밋/스냅샷과 작업 트리 변경]
목적: 기능별 업무 명세와 근거·관계 기록
출력 위치·쓰기 범위: [작성]
실행 제한: 원본 읽기 전용, [설치/실행/DB/외부 접속 제한 작성]

화면 진입부터 결과 반영까지 실제 호출·설정 해석 경로를 추적하라.
공통 JavaScript의 프레임 컨텍스트와 로딩 순서,
요청 식별자의 조립·해석 및 XML 선택 규칙을 확인하라.
업무 규칙·분기·권한·데이터와 상태 변경·실패 처리를 근거와 연결하라.
명세는 이 문서의 기능 양식을 따르고, 사실·추정·미확인을 구분하라.
끊긴 경로와 미조사 범위를 남기고 기존 사용자 설명·메모를 보존하라.
실행하지 않은 동작을 검증 완료로 표현하지 말라.
```
