# demo.md 항목별 역할 안내

[demo.md](demo.md)는 운영 시스템을 조사할 때 필요한 입력과 지식베이스 작성 기준을 정하는 템플릿이다. 이 문서는 각 번호의 목적, 작성 주체와 사용 시점을 설명한다. 모든 항목을 사용자가 처음부터 완성해야 하는 것은 아니다. 알고 있는 정보를 제공하고, 코드에서 확인해야 할 부분은 agent가 조사해 보완한다.

## 전체 구성

| 번호 | 역할 | 주로 사용하는 시점 |
|---|---|---|
| 1 | 조사를 시작할 최소 정보 제공 | 첫 조사 전 |
| 2 | 조사 경계·원본 기준·권한 고정 | 첫 조사 전, 범위 변경 시 |
| 3 | 시스템 특유의 실행 연결 방식 정의 | 대표 기능 조사 중 |
| 4 | 조사 대상과 작업 진행 상태 관리 | 조사 시작부터 종료까지 |
| 5 | 기능별 업무 명세의 내용·구성 통일 | 명세 작성 시 |
| 6 | 주장별 근거·확실성·조사 상태 관리 | 모든 설명·관계 작성 시 |
| 7 | 기능·코드·데이터 사이의 관계 표현 통일 | 관계 정리 및 후속 변환 시 |
| 8 | 누락·오류 검사와 완료 판정 | 저장·인수인계 전 |
| 9 | 변경 영향에 따라 필요한 부분 갱신 | 최초 생성 이후 |
| 10 | 담당 책임과 산출물 구분 | 작업 설계·배정 시 |
| 11 | 채운 기준을 실제 조사 요청으로 전달 | agent에 작업을 맡길 때 |

## 1. 먼저 채울 최소 입력

**역할:** agent가 어디에서 조사를 시작해야 하는지 알려준다.

소스 루트, 대표 JSP, 대응 JS, 공통 include.js, 서버 요청과 연결 XML 중 알고 있는 위치를 적는다. 전체 시스템 구조를 미리 설명하는 항목이 아니라 대표 기능 하나를 추적할 출발점을 주는 항목이다.

사용자가 알고 있는 경로와 실제 예시를 제공하고, agent가 불명확한 연결을 조사한다. 위치를 모르면 `미확인`으로 남긴다. 이 입력이 없으면 조사 시작점을 찾는 데 시간이 들고 사용자가 의도한 기능과 다른 범위를 조사할 수 있다.

## 2. 분석 범위와 기준

**역할:** 무엇을 어디까지, 어떤 원본 상태를 기준으로 조사하는지 고정한다.

화면·서버·공통 라이브러리가 다른 저장소에 있는지, 조사할 기능과 제외 범위는 무엇인지, 커밋이나 스냅샷은 무엇인지 기록한다. 출력 위치와 원본 수정·실행·외부 접속 제한도 정한다.

사용자는 목적·허용 범위·환경 정보를 제공하고, 프로그램이나 agent가 원본 기준과 실제 변경 상태를 확인한다. 이 기준이 없으면 서로 다른 버전이나 환경의 설정을 섞거나 부분 조사를 전체 완료로 오해할 수 있다.

## 3. 시스템 연결 규칙 입력

**역할:** 이 시스템에서 실제 실행 대상을 찾는 방법을 설명한다.

JSP와 JS의 대응 방식, iframe의 함수 접근 컨텍스트, include.js 로딩 순서, 요청 이름을 XML 서비스로 해석하는 규칙 등을 기록한다. import 관계만으로 찾기 어려운 실행 연결을 따라가기 위한 기준이다.

사용자가 알고 있는 관례를 먼저 제공하고, agent가 코드·설정의 실제 예시와 해석 근거로 확인한다. 예를 들어 JS의 자원명과 XML ID가 같더라도, 그 값을 서비스 선택에 사용하는 코드가 확인되지 않으면 연결 후보로 남긴다.

**1번과의 차이:** 1번은 “대표 파일과 요청이 어디에 있는가”, 3번은 “그 자료들이 어떤 규칙으로 연결되는가”를 다룬다. 확인된 규칙에는 적용 범위·환경·예외도 함께 적는다.

## 4. 조사 목록과 기능별 작업 배정

**역할:** 어떤 파일·기능을 조사했고 무엇이 남았는지 관리한다.

파일 존재 확인, 구조 추출, 의미 조사 상태를 구분하고 각 파일이 어느 기능에 참여하는지 연결한다. 조사 작업은 JSP·JS·XML·서버 코드를 기능의 처리 경로에 맞춰 함께 배정한다.

프로그램은 파일 목록을 수집하고, 작업을 조율하는 담당자는 범위를 배정하며, agent는 실제 조사 상태를 기록한다. 파일 목록에 포함됐거나 parser가 성공했다고 업무 의미까지 확인한 것은 아니다.

**2번과의 차이:** 2번은 조사 범위의 약속이고, 4번은 그 범위에서 실제로 수행한 작업과 진행 상태를 기록한다.

## 5. 기능별 업무 명세 양식

**역할:** 기능마다 설명의 질문과 구성을 통일한다.

목적·입력·권한·처리 흐름·분기·데이터와 상태 변화·결과·오류·다른 기능과의 관계를 같은 양식으로 작성한다. 어떤 기능은 정상 흐름만 있고 다른 기능은 예외 처리까지 있는 식의 편차를 줄이는 기준이다.

Agent가 실제 코드와 설정을 조사해 작성하고, 시스템 담당자가 업무 의도나 운영 관례를 확인할 수 있다. 해당하지 않는 항목은 이유와 함께 `해당 없음`, 확인하지 못한 항목은 `미확인`으로 남긴다.

이 항목이 사람이 읽을 핵심 산출물이다. 파일별 설명은 이 명세의 근거와 보조 설명으로 연결한다.

## 6. 근거·확실성·조사 상태

**역할:** 각 설명을 믿을 수 있는 범위와 다시 확인할 방법을 남긴다.

주장마다 원본 경로·식별자·hash·조사 기준을 연결하고, 코드 확인·문서 명시·추정·미확인을 구분한다. 조사 상태는 확인됨·부분 조사·재확인 필요로 별도 기록한다.

예를 들어 정적 코드에서 확인한 입력 검사는 `코드 확인`으로 기록할 수 있지만, 실제 운영 환경에서 그 경로가 실행되는지는 별도 미확인 사항일 수 있다. 프로그램은 hash와 참조를 검사하고, agent는 근거가 설명을 뒷받침하는지 조사한다.

**5번과의 차이:** 5번은 무엇을 설명할지 정하고, 6번은 그 설명의 출처와 확인 수준을 정한다.

## 7. 관계 데이터 작성 기준

**역할:** 명세 안의 연결을 탐색·영향 분석에 사용할 수 있는 관계로 정리한다.

기술 실행, 데이터 읽기·쓰기, 기능 의존, 공통 사용과 업무 의미를 구분한다. 관계마다 출발점·도착점·조건·근거·상태를 기록한다. 같은 공통 JS나 테이블을 쓴다는 이유만으로 업무상 선행·후속 관계를 만들지 않는다.

Agent가 관계의 의미를 조사하고, 후속 프로그램이 정해진 규격으로 검사·변환한다. 현재 템플릿의 관계 분류는 설계안이며 뷰어용 JSON 규격이 구현됐다는 의미는 아니다.

**3번과의 차이:** 3번은 연결을 찾아내는 시스템 규칙, 7번은 찾아낸 연결을 기록하는 표현 기준이다.

## 8. 일관성 검사와 완료 기준

**역할:** 결과가 갖춰야 할 조건과 조사 종료 기준을 정한다.

배정된 범위의 누락, 존재하지 않는 참조, 끊긴 처리 경로, 근거 없는 업무 규칙, 조사 기준과 상태의 불일치를 확인한다. 확인하지 못한 부분도 이유와 다음 확인 위치를 남겼는지 검사한다.

프로그램은 형식·경로·참조를 검사하고, agent나 검토 담당자는 흐름·분기·근거의 내용을 확인한다. 일부 경로가 막혔으면 해당 기능은 부분 완료로 보고할 수 있다. 형식 검사 통과를 업무 설명의 정확성 보장으로 표현하지 않는다.

## 9. 부분 갱신과 변경 영향

**역할:** 최초 생성 이후, 코드가 바뀌었을 때 다시 조사할 범위를 결정한다.

JSP·JS뿐 아니라 include.js, XML 매핑·로딩 순서, 공통 서비스와 데이터 접근 변경을 연결된 기능까지 따라간다. 확인된 관계를 갱신 후보 선정에 사용하고, 실제 영향은 다시 조사한다.

프로그램이 변경 파일·hash·연결 후보를 찾고, agent가 영향을 확인해 해당 주장과 명세를 갱신한다. 재확인하지 않은 부분은 이전 조사 기준을 유지하며 필요한 항목을 `재확인 필요`로 표시한다. 이력과 사용자 메모도 보존한다.

최초 생성 때도 이 기준을 정해 두어야 이후 갱신에 사용할 근거와 관계를 남길 수 있다.

## 10. 역할과 산출물

**역할:** 사람이 제공할 정보, agent가 조사할 내용, 프로그램이 검사·저장할 내용을 구분한다.

시스템 담당자는 실제 관례와 업무 의도를 제공하고, agent는 원본을 조사해 명세를 작성한다. Skill은 작성 절차를 고정하고, 프로그램은 파일 목록·근거·변경·참조와 저장을 관리한다. 뷰어는 결과를 탐색하게 한다.

책임을 나누는 기준이며 각 역할마다 새 agent나 skill을 만들어야 한다는 뜻은 아니다. 기존 지식베이스 agent와 전용 skill을 먼저 활용한다. 문서 색인·기능 명세·조사 목록·미확인 질문 등 필요한 산출물도 여기에서 정한다.

## 11. 채운 뒤 사용할 작업 요청 예시

**역할:** 앞에서 정한 기준을 실제 작업 지시로 묶는다.

대상 루트·기능·자료·조사 기준·출력 위치·실행 제한을 채운 뒤 agent에 전달하는 요청 양식이다. 원본을 어떻게 추적하고 무엇을 결과에 남겨야 하는지 함께 전달한다.

이 양식을 작성하는 것만으로 agent가 등록되거나 실행되지는 않는다. 실제 실행 환경에서 작업을 맡기며, 상세 기준은 채운 `demo.md`를 함께 참조하게 한다.

## 권장 작성 순서

1. **1·2번:** 대표 기능의 시작점과 조사 범위를 먼저 정한다.
2. **3번:** 알고 있는 연결 관례를 적고 대표 기능에서 실제 규칙을 확인한다.
3. **5·6·8번:** 작성할 명세, 근거 표현과 완료 기준을 정한다.
4. **10·11번:** 담당 책임을 정하고 조사 요청을 전달한다.
5. **4번:** 조사하는 동안 목록과 진행 상태를 갱신한다.
6. **7번:** 확인된 기능 흐름과 명세를 관계 데이터로 정리한다.
7. **9번:** 이후 원본 변경에 따라 필요한 부분을 재확인한다.

처음에는 모든 칸을 채우기보다 대표 화면 하나의 실제 흐름을 끝까지 조사한다. 그 과정에서 확인된 규칙을 다른 기능에 적용하되, 동일한 구조라고 판단할 근거와 예외를 함께 확인한다.
