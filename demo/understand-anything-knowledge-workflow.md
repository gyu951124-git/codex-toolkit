# Understand Anything의 지식베이스 생성 방식과 활용 방향

작성일: 2026-10-10  
참조 기준: Understand Anything 커밋 `ffa2f0a84a85525623e9f94f7a6b560e39ae43ce`

이 문서는 원본에서 확인한 분석 방식, 현재 워크스페이스의 구현 상태, 운영 시스템의 업무 명세를 만들기 위한 제안을 구분해 정리한다. 새로운 구현을 완료했다는 의미는 아니다.

## 1. 핵심은 조사·검사 절차를 고정하는 것이다

Understand Anything의 핵심은 AI가 코드를 읽는 순서와 범위, 결과 형식, 검사·저장 절차를 정해 둔 것이다. 일반적인 분석 요청에서도 같은 절차를 적용하면 일관성을 높일 수 있다. 특정 도구를 사용한다는 사실만으로 모델의 업무 이해력이 높아지는 것은 아니다.

“전체 코드를 분석해서 정리해줘”라는 요청만으로는 조사 범위와 설명 수준이 실행마다 달라질 수 있다. 어떤 파일을 읽었는지, 어떤 관계를 확인했는지, 무엇을 조사하지 않았는지 관리하는 장치가 필요하다.

## 2. 원본에서 확인한 일관성 장치

| 장치 | 역할 | 기대되는 효과와 한계 |
|---|---|---|
| 파일 목록과 제외 범위 수집 | 조사 대상과 제외 대상을 정리한다. | 조사 누락을 찾는 기준이 된다. 목록에 포함됐다는 사실은 의미 조사 완료를 뜻하지 않는다. |
| parser 기반 구조 추출 | 함수·클래스·import 등의 정보를 코드 문법에서 수집한다. | 구조를 추측하는 부담을 줄인다. 미지원 언어·동적 호출·추출 실패는 별도 확인이 필요하다. |
| 연결된 파일의 분석 묶음 | import 그래프를 바탕으로 파일을 묶고 다른 묶음의 참조 정보도 전달한다. | 관련 코드를 함께 조사하도록 돕는다. import 연결이 업무 경계를 그대로 나타내지는 않는다. |
| 단계별 agent 지침 | 파일 분석, 병합·검토, 아키텍처 정리, 탐색 순서 생성 등을 나눈다. | 조사 순서와 산출물의 역할을 일정하게 만든다. agent 수 자체가 정확성을 보장하지는 않는다. |
| 결과 병합과 규격 검사 | ID와 관계를 정규화하고 잘못된 참조 등을 검사한다. | 결과를 일관된 데이터로 다루게 한다. 업무 설명의 진실 여부는 형식 검사로 확인할 수 없다. |
| 변경 추적과 증분 검사 | 변경된 범위를 다시 조사하고 심볼 누락 등을 검사한다. | 전체 재작성의 부담을 줄인다. 변경 영향의 의미를 판단하는 조사는 여전히 필요하다. |

원본의 큰 흐름은 사전 확인 → 범위 수집 → 분석 묶음 구성 → 파일 분석 → 병합·검토 → 아키텍처 정리 → 탐색 순서 생성 → 검사·저장이다. 전체 분석, 증분 갱신, 명시적 검토 옵션에 따라 실행 단계가 달라진다. 모든 단계에서 항상 별도 검토 agent를 호출하는 방식은 아니다.

## 3. 구조 지도와 업무 명세의 차이

파일·함수의 연결은 업무 명세를 조사하는 출발점이다. 호출 관계만으로 업무 규칙과 처리 의미를 확정할 수는 없다.

예를 들어 `주문 서비스 → 재고 서비스`라는 연결을 발견해도, 다음 내용을 자동으로 확정할 수는 없다.

- 어떤 조건에서 재고를 예약하거나 차감하는가?
- 결제 실패 시 어떤 데이터를 복구하는가?
- 재시도나 중복 요청은 어떻게 처리하는가?
- 다른 기능·배치·외부 시스템에 어떤 영향을 주는가?

위 예시는 설명용이며 현재 분석한 예제 프로젝트에서 확인한 사실이 아니다. 실제 업무 명세에는 진입점, 호출 순서, 조건 분기, 데이터 변경, 오류·복구 처리와 관련 코드 근거가 함께 필요하다.

구분해야 할 품질 기준은 다음과 같다.

- **구조 정확성:** 파일·함수·참조가 실제로 존재하는가?
- **형식 일관성:** 항목과 관계가 정해진 규격을 따르는가?
- **업무 설명 정확성:** 설명한 조건·규칙·흐름이 실제 구현과 일치하는가?
- **조사 범위의 명확성:** 무엇을 확인했고 무엇이 미확인인가?

앞의 두 기준을 통과해도 뒤의 두 기준을 만족했다고 판단하면 안 된다.

## 4. 현재 워크스페이스의 구현 상태

현재 프로젝트는 원본 전체 저장소와 agent 절차를 그대로 실행하는 구성이 아니다. 고정 커밋에서 필요한 코드를 재사용하고 로컬 지식 관리 기능을 추가했다.

| 구분 | 현재 구성 |
|---|---|
| 원본 재사용 | parser, 구조 그래프 생성, 검색·저장 코드, React 화면, 로컬 뷰어 서버 |
| 프로젝트 추가 | 지식 기록 규격, 근거 hash와 조사 상태, 생성·부분 갱신 실행기, 세대별 저장, 문서·근거 조회 |
| 의미 조사 담당 | 기존 `codebase_knowledge_builder`와 전용 `maintain-codebase-knowledge` 절차 |
| 원본에서 미도입 | 원본 agent·skill 지침, 설치기, hook 등 |
| 뷰어 위치 | `viewer/`에 화면·서버·검증·패키징을 분리 |

원본 helper를 보관하고 있다는 사실은 현재 실행기가 원본의 모든 helper와 agent 단계를 호출한다는 의미가 아니다. 현재 실행기는 원본 분석 코어와 별도로 작성한 지식 관리 절차를 연결한다.

의미 분석은 이 세션의 전용 agent에 작업을 맡기고 결과를 반영할 수 있다. 로컬 명령으로 자동화하려면 해당 환경의 agent 실행기를 별도로 설정해야 한다. 실제 내부망 모델 연결까지 검증된 상태는 아니다.

뷰어는 저장된 지식 데이터를 읽으므로 열람 시 agent가 필요하지 않다. 현재 로컬 뷰어는 Node.js와 브라우저로 실행한다. 분석 실행기와 뷰어에 외부 모델 API 호출 코드를 추가하지 않았으며, 연결하는 agent 실행기의 통신 방식은 해당 환경 설정에 따른다.

## 5. 운영 시스템 지식베이스의 구성 제안

운영 시스템의 동작 명세가 목적이라면 파일보다 기능·업무 개념을 문서의 중심 단위로 삼는 편이 적합하다.

| 중심 단위 | 기록할 내용 |
|---|---|
| 시스템 개요 | 시스템의 역할과 경계, 주요 구성 요소, 외부 시스템 |
| 기능 명세 | 시작 조건, 입력·출력, 권한, 업무 규칙, 정상·예외 흐름 |
| 데이터·상태 | 핵심 데이터 관계, 상태 전이, 읽기·쓰기 주체 |
| 기능 간 관계 | 선행 조건, 공유 데이터, 이벤트 전달, 후속 처리와 영향 |
| 미확인 사항 | 업무 의도 질문, 코드·문서 불일치, 조사 누락과 추가 확인 대상 |

모든 파일은 조사 목록으로 관리하되, 각 파일에 동일한 수준의 상세 문서를 강제하지 않는다. 파일·함수·스키마는 기능 설명의 근거로 연결하고, 공통 인증·트랜잭션 등 별도 설명이 필요한 부분은 주제 문서로 정리한다.

확실성은 코드 확인·문서 명시·추정·미확인으로 구분한다. 조사 상태는 확인됨·부분 조사·재확인 필요로 별도 관리한다. 확인된 코드를 바탕으로 기록했더라도 실행하지 않은 동작이나 운영 환경은 검증 완료로 표현하지 않는다.

## 6. Agent·skill·프로그램·뷰어의 역할 제안

| 구성 요소 | 맡길 역할 |
|---|---|
| Agent | 코드를 조사하고 기능별 업무 규칙·흐름·데이터 관계를 근거와 함께 설명한다. |
| Skill | 조사 항목, 업무 명세 형식, 확실성·상태 구분, 부분 갱신 기준을 고정한다. |
| 변환·검사 프로그램 | 명세의 필수 항목과 참조를 검사하고 뷰어용 데이터로 변환한다. |
| 뷰어 | 기능 지도, 흐름, 상세 명세, 문서와 원본 근거를 탐색하게 한다. |

우선 기존 지식베이스 agent와 전용 skill을 보강하는 방향을 검토한다. 역할 차이가 확인되기 전에 agent·skill을 늘릴 필요는 없다. 반복 가능한 포맷 변환은 프로그램이 담당하고, 업무 의미 판단은 조사 절차에서 다룬다.

권장 순서는 업무 명세 형식 정의 → 기존 agent·skill 조정 → 작은 프로젝트로 작성 품질 확인 → 변환·저장 규격 조정 → 뷰어 조정이다. 현재 분석·근거·변경 추적 기반을 재사용하되, 업무 명세 작성 기준과 뷰어 구성은 아직 확정·구현되지 않은 제안이다.
