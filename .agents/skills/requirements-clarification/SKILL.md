# 요구사항 구체화

주 agent가 질문·계획 단계에서 적용한다. 구현 요청에서도 핵심 동작이나 범위를 정할 수 없을 때 필요한 부분만 이 단계로 연결한다. 실행 요청 자체가 없으면 조사·제안·계획까지만 진행한다.

## 적용 판단

- 기존 대화, 확정 결정과 관련 프로젝트 자료를 먼저 확인한다. 사용자가 기술 설계까지 제공할 필요는 없다.
- 요청이 명확하면 바로 요청된 작업을 진행한다. 논의가 없다는 이유로 작업을 작다고 판단하거나 문답을 추가하지 않는다. 사소한 구현 선택은 프로젝트 관례와 근거에 따라 결정한다.
- 목적과 필요한 범위를 특정할 수 없는 요청은 구체화한다. 예를 들어 “회원 기능 만들어줘”에서 대상 사용자와 필요한 기능을 알 수 없으면 범위를 확인하고, “저장 버튼 문구를 바꿔줘”처럼 명확한 수정은 직접 처리한다.
- 위임받은 agent는 담당 계약의 핵심 정보 누락을 주 agent에게 반환한다. 직접 다른 개발 절차를 선택하거나 사용자와 전체 요구사항 논의를 다시 시작하지 않는다.

## 질문과 제안

- 결과를 크게 바꾸는 미결정 사항부터 적은 수의 질문으로 확인한다. 목적, 사용 주체, 핵심 사용 흐름, 필요한 결과와 제약 중 현재 부족한 것만 묻는다. 이미 답한 내용을 다시 묻지 않는다.
- 질문과 함께 구체적인 범위나 사용 시나리오를 제안한다. 선택지가 있으면 추천안과 이유를 쉽게 설명하고, 사용자가 기술 용어를 몰라도 결정할 수 있게 한다. 선택지는 사용자가 다른 답을 할 수 있도록 열어 둔다.
- 기존 코드와 제약으로 판단할 수 있는 기술 선택은 조사한 뒤 제안하거나 직접 결정한다. 사용자가 답하지 않은 중요한 선택을 승인으로 간주하거나 필수 기능을 임의로 확정하지 않는다.
- 사용자가 확인한 요구사항, agent 제안, 미확인 가정과 이번 제외 범위를 구분한다. 계획에 필요한 기대 동작과 완료 확인 방법을 정리하되 별도 파일·양식을 강제하지 않는다.

## 종료와 인계

핵심 동작과 범위, 완료 확인 방법을 정할 수 있으면 구체화를 끝낸다. 질문·계획만 요청받았으면 정리한 결과를 전달하고 종료한다. 원래 구현 요청이 있고 필요한 결정이 확정되었으면 해당 승인 범위의 구현·수정을 이어가며 같은 승인을 반복해서 요구하지 않는다. 중요한 미결정 사항이 남으면 그 결정에 의존하는 작업은 진행하지 않는다.

주 agent는 개발 절차 선택 규칙에 따라 결과를 인계한다. Spec Kit을 선택한 범위에서는 설치된 공식 명세·명확화 절차와 기존 산출물을 활용하고 별도 명세나 문답을 중복 생성하지 않는다. 일반 구체화 중 Spec Kit 선택이 필요해지면 그때까지의 결정과 미결정 사항을 전달한다.
