# 코드 구현

## 변경 방향

- 요구된 동작과 관련 코드·설정을 확인하고 기존 구조와 스타일에 맞춰 변경한다. 버그는 가능한 범위에서 발생 조건과 원인을 확인한다.
- 새 함수·모듈·의존성 전에 기존 유틸리티와 기능으로 해결할 수 있는지 확인한다. 현재 요구사항에 필요하지 않은 추상화, 설정 옵션과 확장 구조를 만들지 않는다.
- 요청과 관련된 원인을 해결하는 데 필요한 범위를 변경한다. 변경량을 줄이기 위해 원인을 숨기는 임시 우회책을 추가하지 않는다. 요청 범위 확대가 필요하면 이유와 변경 대상을 설명한다.
- 공개 API, 저장 형식과 호출부가 영향을 받으면 기존 사용 계약을 확인한다. 근거 없는 호환 계층이나 예외 처리를 추가하지 않는다.

원인이 불명확하거나 수정 후 같은 문제가 반복되면 재현 조건과 관찰 증거를 정리하고, 원인 가설을 세워 허용된 범위에서 확인한 뒤 수정한다. 확인 없이 여러 변경을 한꺼번에 적용하지 않는다. 실행이 금지되거나 재현할 수 없으면 코드·기존 자료에서 확인한 사실과 미확인 가설을 구분한다.

## 최소 변경과 스타일 보존

- 요청과 무관한 주변 코드, 이름, 주석과 포맷을 정리하지 않는다.
- 개인적 선호보다 해당 파일의 기존 스타일과 패턴을 따른다.
- 이번 변경으로 불필요해진 코드만 정리한다. 기존의 무관한 미사용 코드는 임의로 삭제하지 않는다.
- 기존 기능과 프로젝트 관례를 우선하고, 적합한 표준 라이브러리·플랫폼 기능으로 해결할 수 있는지 확인한다.
- 변경량을 줄이기 위해 필요한 오류 처리, 검증, 보안과 접근성을 제거하지 않는다.

요구사항을 완전히 해결하면서 불필요한 변경을 줄인다. 줄 수를 줄이기 위해 가독성이나 필요한 동작을 희생하지 않는다.

## 코드와 문서

- 주석은 코드 동작을 반복하기보다 판단 이유, 제약과 주의할 조건을 설명한다.
- 문서는 현재 대화를 모르는 사람이 이해할 수 있도록 최종 동작을 기준으로 작성한다. 변경으로 설명이 부정확해진 관련 문서는 함께 갱신한다.
- 생성 파일은 생성 여부와 원본 위치를 확인한다. 프로젝트의 절차에 따라 원본을 수정하고 허용된 생성 명령으로 갱신한다. 실행이 금지되거나 불가능하면 남은 갱신을 보고한다.

## 마무리

변경 파일과 관련 호출부를 읽어 요구된 동작, 불필요한 변경과 남은 사항을 확인한다. 검증 단계는 프로젝트 지침에서 연결한 `verification`에 따른다. 구현 완료와 동작 검증 완료를 구분한다.
