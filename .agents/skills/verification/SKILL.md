# 변경 검증

## 검증 선택

- 프로젝트 문서, 테스트 설정과 실행 스크립트에서 실제 명령을 확인한다. 특정 언어나 도구를 전제하거나 없는 명령을 만들어내지 않는다.
- 변경된 동작과 영향받는 경계를 기준으로 필요한 검증을 선택한다. 단순 문구 수정에는 읽기 검토로 충분할 수 있다.
- 사용자 지정 실행 범위와 금지를 먼저 적용한다. 테스트 금지이면 실행하지 않는다. 의존성 설치, 외부 서비스 사용이나 데이터 변경이 필요하면 이미 허용된 범위인지 확인한다.

## 테스트 품질

- 테스트는 사용자가 관찰할 수 있는 행동과 실제 버그 재현 조건을 검증한다. 의미 있는 변경에서 기존 검증이 부족하면 필요한 테스트를 추가하되 작성 금지 조건을 따른다.
- 기대 결과는 요구사항과 독립적인 근거에서 정한다. 구현 로직을 복제한 예상값, 핵심 로직 자체의 mock이나 내부 호출만 확인하는 테스트로 동작 검증을 대체하지 않는다.
- 실패를 숨기려고 assert를 약화하거나 기대값을 바꾸지 않는다. 테스트가 잘못된 경우에는 요구사항과 수정 근거를 확인한다.
- 사용자 요청 또는 승인된 작업 절차·계획에서 TDD나 테스트 우선 구현을 명시한 경우 해당 순서를 따른다. 일반적인 테스트 작성 요구만으로 TDD를 강제하지 않는다.

## 실행과 결과

- 변경과 직접 관련된 검사부터 실행하고 영향 범위, 저장소의 필수 검사와 실패 결과에 따라 검증을 넓힌다.
- 변경이나 새로운 우려가 없으면 이미 통과한 검증을 불필요하게 반복하지 않는다.
- 실패 원인을 환경 문제, 확인된 기존 실패와 새 회귀로 구분한다. 확인하지 못한 원인은 추정으로 표시한다. 같은 실패를 새 근거 없이 반복 실행하지 않는다.
- 실행 명령, 검증 범위, 실제 결과와 미수행 항목을 보고한다. 특정 테스트 성공을 전체 테스트 성공으로 확대하지 않는다. 실행할 수 없으면 이유와 남은 확인을 기록한다.
